### Task 1.1: Learn how to use Randoop for unit test generation.

Randoop is a tool for JUnit test generation.
A short usage guide for Randoop is available [here](./tutorials/randoop.md), covering how to generate JUnit tests using Randoop and run them in Eclipse.

#### Requirements: 
1. You need to use Randoop to generate **five different test suites** for the given program.
2. Each test suite must achieve **at least 50% line coverage** and **at least 40% branch coverage** in EclEmma. You may need to explore proper Randoop parameters to achieve the coverage requirements.
3. The five test suites should be different from each other. Randoop parameter `--randomseed` may be helpful.
4. The package name of the generated test suites should be `comp5111.assignment.cut`. Randoop parameter `--junit-package-name` may be helpful.
5. The class name of the generated regression test suite should be `Regression_{i}_Test`, `i` in [0..4]. Randoop parameter `--regression-test-basename` may be helpful.
6. Please only submit and measure the coverage of the **regression tests** generated by Randoop. Do not submit and measure coverage of the error-revealing tests.
7. The five regression test suites should be put in `src/test/randoop<i>` for the `<i>`th test suite, where `0<=i<=4`. Randoop parameter `--junit-output-dir` may be helpful.

#### Submissions: 
Submit the five **regression test suites** generated using Randoop. Store them in the folders `randoop0`, `randoop1`, `randoop2`, `randoop3`, and `randoop4` in `src/test`, respectively. No need to submit the error-revealing tests generated by Randoop.

#### Grading Scheme:

### Task 2: Line coverage measurement using Soot (40%)

Soot is a framework for analyzing and transforming Java programs.
We prepared a short introduction about Soot [here](./tutorials/soot.md). Answers to some common questions are available [here](Assignment1_FAQ.md).

For Task 2, you may refer to an [example test suite](./src/test/example_test) along with its [line coverage](./src/test/example_test/TA-line.txt) collected by our implementation using Soot. You can run your program on this example test suite and crosscheck the coverage results with ours. The coverage reported by your tool should be **close** to ours. 
Besides, we encourage you to **follow the style of our reports** to present the necessary information including the coverage of the whole classes and each line, the detailed numbers of covered and missed lines, etc.

#### Requirements:
1. Use Soot to instrument the given CUT to measure the line coverage of tests.
2. Your program needs to generate a report file, which **at least contains the following information**:
   * The line coverage for the whole `Subject` class (final percentage and raw numbers of the covered and total lines), and the coverage for each of its five inner classes.
   * The coverage of each line (line code, `covered` or `missing`).
   * The line number in the Java source file for each line.
3. You should prepare a one-click script to automatically use your implemented Soot-based tool to report the line coverage of the `example_test` test suite. You should also provide the usage instructions of your one-click scripts, together with the path and meaning of the output files.

#### Notes:
- You can start by recording statement coverage, then extend to line coverage by obtaining each statement's source line number and aggregating coverage information per line.
- When instrumenting the CUT, **you are required to skip the `JIdentityStmt`**. Please refer to [FAQ Q3](./Assignment1_FAQ.md#3-why-we-got-the-exception-javalangruntimeexception-param-assignment-statements-should-precede-all-non-identity-statements-) on why we need to skip the `JIdentityStmt` and the hint on how to skip it. Concretely, do not insert instrumentation probes into statements of type `JIdentityStmt` when traversing a method's body; skip them and insert probes only into non-identity statements.
- To get the line number in Java source file, you can first follow [FAQ Q9](./Assignment1_FAQ.md#9-how-to-preserve-the-line-number-in-soot) to keep the source code line numbers for Soot analysis; then, use proper Soot APIs to get the line numbers of each statement.
- To validate the correctness of your line coverage report, you can crosscheck it with the report generated by EclEmma. The coverage reported by your tool should be **close to** that reported by EclEmma for the classes in the CUT. 
  - *Note it is normal that the number of covered/total lines reported by Soot and EclEmma may not be the same, since Soot and EclEmma consider different types of statements and apply different optimizations to code, and thereby, there could be a small difference (typically within 1%) in their reported coverage.*

#### Submissions:
1. You may put your source code under `comp5111.assignment` package in `src/main/java` folder.
2. **Please prepare useful scripts and README files in the project root**, containing the one-click script and instructions on running your implementation as mentioned in the requirements.
3. You need to measure the line coverage of the example test suite. Then, provide a report to show the differences in the percentage (line coverage for all inner classes) reported by your tool and EclEmma over the example test suite. *Note that: minor differences are allowed for line coverage.*
4. Advice: You are encouraged to maintain your code in a `private` repository at Github. This provides a backup of your code in case your computer crashes and allows us to retrieve code from your GitHub repository in case of submission errors. Such incidents have happened in the past.

#### Grading Scheme:
- `5%` if a clear usage instruction and one-click script are provided to run your Soot-based tool on the example test suite.
- `20%` if your soot-based program can successfully instrument the code and report the coverage following the requirements.
- `15%` if the results reported by your code are correct on the hidden test cases from the teaching team.


### Task 3: Generative AI for specification-based test preparation (35%)

#### Requirements:
1. Explore the usefulness of large language models (LLMs) in specification-based test preparation. We encourage the use of HKUST OpenWebUI `hkgai-v1`-series models free on [HKUST OpenWebUI platform](https://openwebui.hkust.edu.hk/), but other publicly available LLMs are also allowed.
2. Generate test cases based on the current specifications (function docstring, provided in the comment before each function) in `Subject.java`, analyze the limitations of current function docstring for generating effective test cases, and suggest improvements to the specifications to enhance the performance of LLMs in test generation.
3. Write a study report to discuss the observations from your exploration.

#### Concrete Subtasks:
1. **Test Generation Based on Current Specifications (10%):** Select 10–20 functions in `Subject.java`. Design effective prompts (e.g., using few-shot, chain-of-thought, etc.) to make the LLM generate JUnit tests for these functions based on only the function's docstring and signature. The function body is not allowed to be included in the prompt. Since the CUT is a single Java class file, please directly prompt the LLM to realize the goal; there is no need to use advanced techniques such as agent-based decomposition, model context protocol (MCP) and tools, etc.
In your report, please list the LLM and prompt you have used, and discuss how your prompt helps the LLM to generate high-quality test cases compared with using a simple prompt (e.g., a plain instruction and code context).
2. **Analysis of Limitations of Current Specifications for Test Generation (10%)**: Assess the tests generated in subtask 1 by considering test case quality in terms of EclEmma line/branch coverage, assertion correctness, and test effectiveness (e.g., whether tests exercise edge cases, whether tests can reveal certain faults).
In your report, summarize 3–5 common issues in the current specification (e.g., missing certain important details, ambiguous descriptions, etc.), and use concrete examples and quantitative measurements to illustrate your analysis.
3. **Suggestions for Specification Improvement (5%)**: Propose 2–4 concrete ways to enhance function specifications (e.g., clarify (what) input ranges, provide example (what type of) input/outputs, etc.) to help LLMs generate effective tests from specifications. Provide concrete examples to illustrate how each suggestion is realized. At least one enhancement method is expected to be able to be automatically realized by LLMs (based on the function body code and with some code analysis tools, if needed).
4. **Justify Effectiveness of the Enhanced Specifications (10%)**: Enhance the specifications of the selected functions in `Subject.java` based on your suggestions above. You can either design prompts to drive the LLM to automatically enhance the specifications based on function code or manually improve the specifications following some criteria defined by you. Then, prompt the LLM to generate a new set of test cases based on the enhanced specifications, and discuss how these new test cases differ from the previous ones and why your modifications to the specifications help the LLM to generate better test cases.
In your report, please record the prompt or criteria you have used (if any) to enhance specifications, and justify the effectiveness of these enhancements with concrete examples and quantitative measurements.

#### Notes:
- For each of the above subtasks, write a detailed analysis in your report. You are encouraged to include concrete examples, intuitive visualizations (figures), and quantitative measurements to support your analysis, if they apply to the subtask.
- You are suggested to discuss subtasks 1 and 3 in 100-250 words each, and subtasks 2 and 4 in 200-350 words each. These are not hard limits, but please keep your report informative and concise.
- You should use only the specifications (i.e., docstring of each function, the comments before each function code in `Subject.java`) as the basis for test generation. The function implementation code (body) should not be used for test generation. However, you can reference the function body when analyzing the limitations of current specifications and improving the specifications in subtasks 2 and 4.
- Please organize the answer to each subtask in separate sections in your report.

#### Submissions:
Submit a `pdf` file as your report. Name the report document `Task3_Report.pdf` and put it under the root folder of your submission.

#### Grading Scheme:
- For subtask 1, `5%` for the quality of the designed prompt, and another `5%` for the justification of its advantages over a simple prompt.
- For subtask 2, `5%` for the reasonability of the identified limitations, and another `5%` for the justification with concrete examples and quantitative measurements.
- For subtask 3, `5%` for the quality of the suggested improvements and the clarity of the justification.
- For subtask 4, `5%` for the clarity of the enhancement prompt/criteria, and another `5%` if the advantages of the new tests over the previously generated ones are clearly justified with examples and quantitative measurements.
